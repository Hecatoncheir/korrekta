# Исправление непригодных ответов GigaChat 10В

5 ноября 2026 года. Исправление зафиксировано в `dffb1b9`. Повторные 320 случаев завершены: у 10В **54/60 чистых исправлений вместо 47/60**, ответы `{"text":"{"}` исчезли — **26 → 0**. На этом уже известном наборе итоговые тексты 10В и 20В полностью совпали. Одна лишняя стилистическая рекомендация остаётся, поэтому общей безошибочности нет.

## Причина и контролируемые пробы

В приложении обе модели получали один и тот же `gigaPrompt`, вручную составленный для GigaChat 20B-A3B-instruct-v1.5. У GigaChat3.1-10B-A1.8B другой шаблон диалога: явные роли `developer system`/`system`, переводы строк после разделителей и собственная служебная инструкция. Передача чужого уже отформатированного запроса с `raw:true` обходила правильный шаблон 10В.

Это проверено при неизменных весах, Ollama 0.40.4, инструкции корректуры, JSON Schema, seed 42, temperature 0 и контексте 8192. В [диагностическом журнале](diagnosis/wire.jsonl) сохранены запросы и ответы четырёх заранее выбранных случаев:

| Изменение относительно старого запроса | Результат |
| --- | --- |
| Прежняя JSON Schema и чужой шаблон | Два проблемных случая снова дали `{"text":"{"}`; имя `Севиран` изменено, фраза с Вирмелой перефразирована |
| Только `format:'json'` | Те же ошибки; проблема не устранилась |
| Только снятие ограничения `format` | Ответы с лишним `assistant`, двойными кавычками и повреждённым JSON |
| Только замена содержимого `prompt` на официальный шаблон 3.1, прежний API generate и Schema | Все четыре ответа соответствуют ожидаемому полному тексту |
| Передача тех же двух сообщений в `/api/chat`, прежняя Schema и параметры | Те же четыре правильных ответа |

Контрольный вариант с ручным официальным шаблоном изолирует причину: для устранения этих сбоев не понадобилось менять инструкцию, квантование, модель или Ollama. Ограничение JSON обеспечивало допустимую форму оболочки, но не пригодность содержимого поля `text`.

Официальный шаблон взят из [репозитория ai-sage, ревизия `99ef74e635fb6bf2509ff52760818ea10e8f72c8`](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B/blob/99ef74e635fb6bf2509ff52760818ea10e8f72c8/chat_template.jinja). [Зафиксированная копия](../../../text-response-fix/gigachat31-chat-template.jinja), SHA-256 `e0b8ec1e172a124fe688e705a6e48fc30c575c23dae7388e43007f150d8343a3`. Через `/api/show`, без генерации, сохранён [шаблон установленной GGUF](diagnosis/ollama-model-template.json): он дословно совпал с официальным, все 13787 символов ([сравнение](diagnosis/template-comparison.json)). В приложение этот текст отдельно не встраивается: его применяет Ollama из выбранной модели.

## Что изменено

- Только 10В отправляется в `/api/chat` с отдельными сообщениями system/user. 20В сохраняет прежний ручной шаблон и `/api/generate`. Ответы обоих API приводятся к одному внутреннему виду; идентификатор модели остаётся выбранным пользователем.
- Для обеих моделей заданы `truncate:false` и `shift:false`: переполнение контекста должно завершаться ошибкой, а не незаметным удалением начала запроса. Поддержка этих флагов проверена в [исходниках закреплённого Ollama 0.40.4](https://github.com/ollama/ollama/blob/v0.40.4/api/types.go). Контекст 8192 и параметры генерации сохранены.
- После строгого разбора JSON проверяется пригодность полного текста: пустота, исчезновение всех букв/цифр или потеря более половины длины исходника вызывают отказ. Неизменённый исходник, включая отдельный символ `{`, допустим. Оформление, имена и отдельные правки по-прежнему проверяются прежней защитой; новый фильтр не доказывает смысловую правильность остальных ответов.
- Непригодный ответ записывается как `collection_error`; предложения модели исключаются, предложения словарей и LanguageTool сохраняются. В интерфейсе появляется постоянное «Проверка неполная» вместо утверждения об успешной проверке без ошибок. После успешного повтора предупреждение исчезает.
- Предупреждение находится в прокручиваемой области подсказок; тесты ширины 1280 и 640 подтвердили отсутствие переполнения. Повтор сообщения внизу редактора убран. [Снимок нативного приложения](partial-control.png).

## Проверка предупреждения

Все 320 старых ответов проверены новым валидатором без повторных запросов. Отклонены все 26 ответов с `{` и ещё 8 пустых/сильно обрезанных результатов, включая парные повторы. [Пересчёт](replayed-validation.json), [команда](../../../../tools/model_benchmark/bin/replay_correction_validation.dart).

Четыре из восьми дополнительных отказов относятся к 20В: в двух основных случаях и их повторах со словарём модель вернула только `Имя файла ` или `Метка ` с JSON-пробелами вне строки. Раньше защита сохраняла исходник без предупреждения; теперь пользователь видит неполную проверку. Это изменение честности статуса, а не новая потеря имени.

В нативном Flutter-приложении отдельно подставлен ответ `{"text":"{"}` вместо ответа 10В. Остальные движки настоящие. Проверены ошибочный текст `Я проверел документ.` и правильный `Все службы работают.`: исходник сохранён, предупреждение видно, ложного «Проверка завершена» нет. Карточка `проверил` от остальных источников доступна для ручного выбора; успешный повтор с настоящей моделью убирает предупреждение. Принятие рекомендаций и отмена проверены в полном прогоне 320 случаев. [Журнал подстановок и повторов](partial-proof-wire.jsonl), [сценарий](../../../../app/integration_test/partial_check_test.dart), [результат сценария](partial-proof.json), [снимок со словарными вариантами](partial-spelling.png).

Диагностический сценарий сначала ошибочно ожидал словарное исправление `нравиться → нравится` без участия GigaChat. Он остановился на этом ожидании; для проверки сохранности словарных карточек выбран обычный орфографический пример `проверел`. Изменён только тестовый пример. Все запросы попыток сохранены, подставленные ответы отмечены `injected:true`. Они не входят в повторный языковой набор. Отдельный виджетный тест выявил нехватку высоты предупреждения в узком окне; компоновка исправлена и повторно проверена. После полного прогона диагностический сценарий ещё раз прошёл через `flutter run`, включая горячую перезагрузку на экране предупреждения (`Reloaded 0 libraries`, повторная сборка дерева выполнена за 395 мс). Финальный результат сценария — `All tests passed`.

## Повторная оценка через приложение

[Протокол исправленной версии](../../../text-response-fix/protocol-v1.json) зафиксирован до первого запроса повторного набора. Используется тот же неизменённый [набор](../../../app-quality/cases-v1.jsonl), SHA-256 `2e544aa8a975b250417aa344ec844f1781695154cda564a167a3281df828decf`: 140 текстов и 20 парных повторов на модель, всего 320 случаев. Сравнение с [первым прогоном](../app-quality/README.md) является повторной проверкой на уже известных данных, а не новой независимой языковой приёмкой.

Порядок моделей и текстов, личный словарь, инструкция корректуры и профиль `inflections` прежние. Проверяется настоящий путь UI → EditorCubit → LocalChecker → все локальные движки → карточки → принятие → отмена. Журнал сохраняет оба API. Производственные 84 файла проверяются по SHA-256 до и после выполнения. Изменения этих файлов во время прогона запрещены; завершённые результаты не повторяются ради выбора лучшего ответа. Старые результаты и `benchmarks/best-known.json` сохраняются.

У 10В добавлены семь чистых исправлений без потери прежних полезных результатов: `error-format-3`, `error-format-19`, `error-format-12`, `error-names-6`, `error-format-13`, `error-format-8`, `error-format-18`. Это прежние пропуски около Markdown, отступов, URL, комбинируемого знака и имени Вирмела. Во всех 26 случаях вместо скобки получен текст, прошедший проверку пригодности; из девяти содержащих ошибку текстов восемь теперь исправлены полностью. `error-format-4` остаётся пропуском отбора рекомендации. Все 17 правильных контролей сохранили исходник.

У обеих моделей остаются одни и те же шесть пропусков: `вернулесь → вернулись`, запятая в `не знаю, куда`, `работаит → работает`, `повторяит → повторяет`, латинская `e` в `отвечаeт`, `будит → будет`. В пяти случаях правильная альтернатива доступна в карточке, но не рекомендована. Одна и та же лишняя рекомендация на правильном тексте — `рожденья → рождения`. Других неверных изменений ошибочных текстов не обнаружено. Разбор прежнего режима находится в [первом отчёте](../app-quality/README.md).

Итоговые тексты всех 160 случаев 20В совпали с её прежним запуском; все 160 результатов текста исправленной 10В совпали с текущей 20В ([сверка](output-comparison.json)). Статус завершённости при этом различается: `control-names-18` у 20В теперь явно помечен как неполная проверка из-за обрезанного модельного текста `Имя файла `. Поэтому 78 полностью проверенных правильных контролей вместо 79 не означает новое повреждение исходника. В парном повторе этого текста со словарём 20В также показала предупреждение. У 10В неполных проверок ни в основном наборе, ни в парных повторах нет.

В опыте со словарём обе модели дали 10/10 чистых исправлений и 0/10 изменённых контролей. Личный словарь убрал прежние четыре ненужные карточки у каждой модели; исходник с намеренным именем файла сохранился и у 20В с предупреждением. Словарь фильтрует предложения, но сам по себе не исправляет содержательный сбой модели.

Сырые ответы до защиты всё ещё содержат ненужные изменения: у 20В — 25/80 изменённых правильных контролей, у 10В — 9/80. На итоговые тексты эти числа напрямую не переносятся: приложение объединяет источники и проверяет допустимость отдельных правок. Защита имён и оформления остаётся необходимой.

Задержки измерены в последовательной Debug-сборке с загрузкой словарей на каждый запрос и без изоляции фоновой нагрузки. Любая фактическая загрузка или перенастройка runner внутри запроса попадает в это время, даже после отдельного прогрева. Например, первый запрос 20В занял 18,177 с. Эти значения описывают запуск приложения и не доказывают отдельное ускорение модели после смены шаблона. Требования RAM/VRAM этим опытом не устанавливались.

На данном повторном наборе исправленная 10В сравнялась с 20В по итоговому тексту, при этом не дала неполных проверок. Объявлять её новым общим эталоном только по знакомым данным рано: после исправления интеграции нужен следующий заранее зафиксированный набор. Сохранённый `best-known.json` и модель по умолчанию не изменены.

Основной сценарий завершился с кодом 0, `All tests passed` ([данные driver](driver-result.json)). Это успешное выполнение сценария, а не прохождение нулевого порога ложных правок. [Итоговые показатели](summary.json), [случаи для разбора](review.json), [парный опыт](personal-comparison.json), [аудит](audit.json). Все 160 запросов 20В действительно отправлены в `/api/generate`, все 160 запросов 10В — в `/api/chat`. Для каждого подтверждены выбранный идентификатор модели, контекст 8192, HTTP 200 и `done_reason:stop`; лимит ответа не достигался. SHA-256 набора и 84 производственных файлов повторно совпали. Веса и Ollama 0.40.4 те же, что в первом прогоне ([окружение](environment.json)).
